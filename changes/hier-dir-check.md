- `dexpireover` and `doverctl clean` with `readergrouphash hierarchy` or `hierarchy-full`: a file is the file of a group only in that group's directory. The file name holds the whole group name, but the two layouts put many groups in different directories (`e2e.x.gz` in `e2e/` or `e2e/x/`, `a.b.c` in `a.b/` or `a/b/`), and the file's directory was not compared. After a switch between `hierarchy` and `hierarchy-full` made by editing `readergrouphash` (`doverctl convert` refuses it), the copies left in the old directories were taken as the groups' files and kept, and `dexpireover` expired the old over file as well as the new one, which moved the group's first article past its last and emptied OVER of the group. Now `dexpireover` and `doverctl clean` remove the old-directory copies after such a switch as the files of no group ("Group for over file not found, removing"), once the group has its over file in its new directory. A group with no over file there yet keeps its old files as before, since a dreaderd started before the change still writes them; for such files `dexpireover` now reads the number of articles per data file from the over file beside them (it used 256 and removed, for example, `d.4.<group>` with dexpire.ctl `e4` as misaligned). The data name `d.<n>.X.gz` (the plain data of a group X.gz, or the compressed data of X) is now judged by the group whose directory it is in: with `hierarchy-full`, and with `hierarchy` for groups like `e2e.foo` and `e2e.foo.gz` (in `e2e/` and `e2e/foo/`), the data files of a removed X.gz are no longer kept as X's, and a stale file in X's directory is removed even when X.gz has articles in that base. Where X and X.gz share a directory (`hierarchy`, `e2e.x` and `e2e.x.gz` in `e2e/`) nothing changes; crc and md5 spools are not affected (D-336).
